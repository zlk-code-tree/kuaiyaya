## 1. 结论摘要

做一款名为「快鸭鸭」的本地桌面小应用（logo 用一只小黄鸭）：拖入或选择一支视频，按用户指定的目标大小压缩，并在「压缩要快」和「画质要高」这两点上同时成立。文件全程在本机处理，不上传。第一版功能保持简单——只处理单个文件，读到原片后默认把目标设为原大小的一半，用户可用数字或滑条调整——但第一版的首要目标不是功能覆盖面，而是在这条简单路径上把速度和画质做扎实。

为谁做：需要把拍摄、导出或下载来的大视频压到可发送、可提交、可存档体积的个人用户。他们不一定懂码率或编码器，只关心「能不能压到我想要的大小」「要等多久」「看起来还能不能接受」。典型场景包括邮件附件上限（例如 Gmail、Outlook.com 官方均为 25 MB）、聊天与网盘上传限制、课件/作业提交的体积门槛。个人微信当前官方视频/文件发送上限本轮未从官方帮助中核实到可引用的现行数字，但「发出去之前必须先缩小」这一类需求本身成立。

凭什么能立住：这条赛道的关键不是再做一个万能转码器，而是把「指定目标大小 + 本地处理 + 尽量保画质 + 还要快」做成一个几乎不用决策的动作。2026 年 10 月起，[CompressO](https://compresso.codeforreal.com/) 已在免费、本地、跨平台的产品里提供 Target Size，并叠加菜单栏、文件夹监视、预设、硬件加速等能力，是最直接的对标。我们不靠功能清单取胜，也不把「唯一能指定目标大小」当作卖点（这已经不成立）。差异要落在三处：交互上只问一个问题（压到多大），默认从「原片一半」起步而不是先让用户猜一个上限；编码上以速度和画质为第一期成功标准，并用可验证的方式在软编双遍与硬件加速之间做取舍；输出上给出明确、可分享的约定（1080p 上限、HEVC、`hvc1` + `faststart`），用户不必自行搭配参数。

三期怎么切：

- **第一期（MVP）**：功能范围严格对齐现有原型与第一版需求，只做单文件主路径。首要目标是「快」和「画质高」，以及目标体积可控。原共识中的「硬件加速第一版明确不做」在本方案中重新评估，但不暗改已有技术定案；默认编码路径须在 libx265 软编双遍与硬件加速（macOS 上优先评估 VideoToolbox）之间，按验证结果由昆哥拍板。第一期就要有开通机制：不做登录、不做账号，用户输入服务端分发的 Key 即可使用；Key 可设有效期，到期自动失效。绑定成功后按无感校验（可由昆哥改）：以后打开直接进主界面，后台静默校验，不弹开通页；只有失败才有感。第一期还要有可找到的关于/反馈入口：写清维护者「黑曼巴的紫金王朝」，反馈为邮箱 zhanglikunmamba@gmail.com + 微信扫码。不做成账号体系。批量、预设管理、自定义输出路径仍不做。
- **第二期**：在第一期已经能又快又好地处理好「一支视频」之后，再让用户更高效地处理更多文件——批量队列、常用体积预设、可改输出位置与命名；若第一期未能上硬件加速，第二期再补上已经验证过的加速路径。
- **第三期**：减少「压完才知道好不好看、能不能播」的意外，例如压缩前后对比、更多输出规格（兼容性或更低分辨率档），以及目标过小时的画质风险提示。

本方案沿用原型中的 10 条默认假设，并全部标为仍待昆哥确认。另有本方案新增确认项，其中最关键的是：第一期默认编码路径（软编双遍还是硬件加速）、目标体积允许的误差（尤其是「不得超过目标」还是「大致接近」）、是否首先只做 macOS。第一版产品名已定为「快鸭鸭」，logo 用一只小黄鸭。关于与反馈已拍板：维护者是「黑曼巴的紫金王朝」；反馈为邮箱 zhanglikunmamba@gmail.com + 微信扫码（二维码见第 5.1.3 节）；第一期要有可找到的关于/反馈入口，不做成账号体系。设备绑定细则已由昆哥小弟代为拍板（昆哥可随时改）：一对一（一台电脑只匹配一个 Key，一个 Key 同时只绑定一台电脑）；换机和重装须管理员在服务端解绑后重绑原 Key，不自动解绑、不强制换发；本机再输入另一枚 Key 则拒绝；第一次成功校验即绑定。已拍板的其他开通规则：使用 Key 时断网不能使用，网络用于校验 Key 的合法性，上次校验通过不能当离线通行证；Key 过期只是不能压缩，仍可打开应用、查看或打开已有文件；Key 只发给内部人、先小范围试用、不对外销售；校验失败须分开提示「网络不通」和「Key 无效或过期」。无感校验已拍板（可由昆哥改）：第一次仍要输入 Key；绑定成功后打开应用直接进主界面，对已绑定 Key 在后台静默校验，不弹开通页、不打断操作；点「开始压缩」时若这次打开后已静默校验通过则直接开始、不再弹出「校验中」，若后台校验还没完成则只在开始按钮上短暂等待、不进开通页、不大弹窗；只有失败才有感。

## 2. 产品定位

**一句话**：快鸭鸭把本地视频快速压到指定大小，并尽量保住观感。

**名称与标识（已拍板）：** 产品名叫「快鸭鸭」，logo 用一只小黄鸭。

**关于与反馈（已拍板）：** 维护者是「黑曼巴的紫金王朝」。反馈为邮箱 zhanglikunmamba@gmail.com + 微信扫码（二维码见第 5.1.3 节）。第一期要有可找到的关于/反馈入口，不要做成账号体系。

这不是通用视频转码器，也不是剪辑工具。第一版只回答一件事：用户指定一个目标体积后，应用用尽可能短的时间，给出尽可能好的画质，并让结果接近（理想情况下不超过）这个体积。

已有、且本方案不擅自改写的技术框架：

- 形态：桌面小应用「快鸭鸭」，Electron + 本地 ffmpeg；logo 用一只小黄鸭
- 处理位置：全部在本机完成，文件不上传
- 既有编码定案：`libx265` 双遍编码；输出 1080p HEVC `.mp4`，带 `hvc1` 标签和 `faststart`
- 目标大小：读到原片后默认压到原大小的一半，可用数字或滑条调整；不要默认 300 MB
- 第一版功能边界：单文件、可调目标、开始/取消、两遍（或与所选编码路径相匹配的）进度、完成结果。批量、预设管理在第一版仍不做
- 开通机制（已定方向）：不做登录、不做账号；用户输入服务端分发的 Key 即可使用；Key 可设有效期，到期自动失效。绑定成功后做无感校验（可由昆哥改，细则见第 5.1.2 节）。视频文件仍不上传，与服务端的交互仅用于 Key 校验

需要立刻写清的一点：既有定案把硬件加速列在第一版明确不做，编码路径按 libx265 双遍来写。昆哥随后把产品核心明确为「压缩速度快」和「视频质量高」。这两点与「第一期不上硬件加速」存在张力。本方案不在文中偷换定案，而把这道交替单列（见第 5.1.1 节，以及第 7.3 节仍待确认项），建议先做对比验证再决定第一期的默认路径。

产品要守住的承诺：

1. **指定目标大小是一等公民**，不是码率、CRF、预设里的附带项。
2. **本地、不上传**，进度区始终保留这句说明，避免被理解成在线压缩。
3. **速度和画质同时作为第一期的产品承诺**，技术选型为这两点服务，而不是为了功能完整。
4. **输出约定清晰、少决策**：第一版不开放编码器、分辨率、帧率的自由组合；用户只调目标大小。
5. **用 Key 开通，不用账号**：第一期就要能控制谁在用，但不做成登录和账号体系。绑定成功后做无感校验（可由昆哥改）：以后打开直进主界面，后台静默校验；第一次输入没法无感，只有失败才有感。

## 3. 目标用户与典型场景

目标用户是需要把过大的本地视频变小，以便发送、提交或存档的个人。他们通常不配置编码参数，判断标准是：有没有压到目标、等多久、看起来是否还能用。本轮没有做用户访谈或问卷，以下场景来自产品推理和已核实的平台限制，不作为调研统计。

**邮件附件。** 个人 [Gmail 官方帮助](https://support.google.com/mail/answer/6584?hl=zh-CN) 写明附件上限为 25 MB（多个附件合计亦然），超出后会改为 Google 云端硬盘链接。[Outlook.com 官方说明](https://support.microsoft.com/en-us/outlook/sending-limits-in-outlook-com) 同样将附件大小限制为 25 MB，更大文件需通过 OneDrive 分享。用户若必须「作为附件发出去」，就需要先把视频压到上限以下。这类场景对「不得超过目标」非常敏感，略超 25 MB 即失败。

**即时通讯与上传表单。** 聊天软件、网盘、表单常常有体积上限。本轮未核实到可引用的个人微信现行官方上限数字（可见公开报道较旧，不宜当作 2026 年现行规则来写）。尽管如此，把一条手机拍摄或 4K 素材压到「对方能直接收下」的体积，仍是最常见的使用动机之一。CompressO 官方也把「邮件或聊天 10 MB / 25 MB」当作 Target Size 的主场景。

**课件、作业、项目提交。** 学校、培训机构和内部系统常对上传视频设体积上限，具体数字因平台而异，本轮不引用某个未核实的门槛。用户往往有明确的「必须小于 X MB」，且交稿时间紧，既不能等太久，也不能压到字迹或投影内容不可读。

**存档与腾出磁盘。** 不一定有硬上限，只是希望明显变小、观感仍可接受。默认「原片一半」比「请输入一个上限」更贴近这类动机；用户仍可再往下调。

**不作为第一优先的用户。** 需要批量转码、字幕压制、多编码器试验、专业片源制作的人，已经有 HandBrake、小丸工具箱、ffmpeg 命令行。第一版不与它们比功能广度。

## 4. 市场对标与差异

调研截止：2026-11-12。只写本轮 WebSearch / WebFetch / curl 核实到的内容；写不清的标明「本轮未核实」。对标重点是「指定目标大小 + 本地 + 尽量保画质（现在还要快）」这条赛道，而不是泛视频转码器大比拼。

### 4.1 我们为什么还要做

指定目标大小这件事，2026 年已经不是空白。CompressO 4.0（[官方博文，2026-10-25](https://compresso.codeforreal.com/blog/compresso-4/)）把 Target Size 做成主功能；VideoProc、Permute 也以不同完整度提供目标体积或文件大小限制；小丸工具箱的社区重制版写明支持「指定目标体积（自动二次编码）」；在线工具如 FreeConvert 也可指定目标体积或按原大小百分比压缩，但文件要上传。

因此，不能把「我们能指定目标大小」或「我们是本地的」当作独特卖点。能立住的差异应是：

1. **只做一件事，决策极低。** 打开即拖入，默认原片一半，调一个数字，开始。不把图像、音频、GIF、监视文件夹、菜单栏、预设体系一并塞进来。CompressO 4 已走向压缩套件；VideoProc、Permute、格式工厂、HandBrake 更是全能工具。简单本身是立场，不是第一期还没做完的借口。
2. **默认语义不同。** 竞品营销多强调「输入 10 MB / 25 MB 这种上限」。我们读到原片后默认压到一半，同时允许用户改成任意合法目标（包括 10 或 25）。这对「先变小再看看」和「就是要卡在某个上限」两种动机都成立，而且避免了已否定的「默认 300 MB」。
3. **速度和画质是产品核心，不是参数页里的可选项。** 第一期的成功不取决于功能数量，而取决于在单文件路径上是否够快、够清晰、体积是否可靠。编码路径（软编双遍 vs 硬件加速）按这个标准来选，不为「功能对等」去堆编码器选项。
4. **输出约定固定、可分享。** 1080p 上限、HEVC、`hvc1` + `faststart`、音频转 AAC。用户不必先学封装标签和兼容性。代价是第一版灵活性低，且 HEVC 在部分旧设备上的可播性需要在方案中诚实说明（见待确认项）。

若产品主要给昆哥自己用，上述差异已经足够指导第一期。若面向更大范围分发，必须正视：CompressO 同时免费、开源、本地、跨平台，并且已经有 Target Size 与硬件加速。功能扩张追平它没有意义；只有把「更快、更好看、更准地压到目标」做成可感知的体验差，才值得做成一个独立产品。

### 4.2 重点竞品

#### CompressO

- **定位**：免费开源的本地压缩应用，官方表述为在 Mac、Windows、Linux 上压缩视频、图片和音频，并可压到精确文件大小；无需注册、不上传、不追踪。[官网](https://compresso.codeforreal.com/)
- **指定目标大小**：支持。4.0 起提供 Target Size：用户输入所需大小；官方说明会先用短样本估算，尽量保持原分辨率，并重试直到符合目标，每次尝试都会保留，可在结果中另选。图片和音频也可指定目标大小。[4.0 博文](https://compresso.codeforreal.com/blog/compresso-4/)
- **本地还是上传**：本地，可离线。官方与 [GitHub README](https://github.com/codeforreal1/compressO) 均写明压缩由本机 FFmpeg 等工具完成，应用不向外部发网络请求（内置更新除外）。
- **主要平台**：macOS（官网写 macOS 13 或更新，提供 Apple Silicon / Intel 安装包，亦可用 Homebrew）、Windows 10/11 64 位、Linux（AppImage 与 Debian/Ubuntu）。技术栈为 Tauri + React，不是 Electron。
- **价格**：官方写明免费且开源，许可证为 AGPL-3.0，无付费档。本轮未见官网标价，故不写币额。
- **适用人群**：希望少调参数、在本地把文件压到某个上限的个人用户；4.0 之后也覆盖需要批量、预设、菜单栏快速压缩的人。
- **对我们的意义**：最近、最像的竞品，必须对标，不能回避。值得学的是：把「目标大小」放在主路径；为正向上限场景准备「尽量不超过目标」的策略（它用估算 + 重试）；保留多种尝试结果供回看。故意不学的是：第一期不要做成图片/音频/监视文件夹/CLI/MCP 套件。另外，[CompressO 4.1.0 更新说明](https://github.com/codeforreal1/compressO/releases) 提到曾修复「macOS 硬件加速结果比原片还大」，以及「H.265 Target Size 不再超出所选大小」。这说明「硬件加速 + 钉死目标体积」是真实工程风险，恰好是我们第一期要验证的问题。其具体默认编码器、是否采用 libx265 双遍，本轮未从官网或 README 核实到，不臆测。

#### HandBrake

- **定位**：开源视频转码器，把几乎任意格式转到一套现代编码器。[官网](https://handbrake.fr/)
- **指定目标大小**：没有作为一等功能的「输入目标 MB」。官方文档把平均码率作为控制体积的方式，并建议除非真正需要瞄准文件大小，否则使用 Constant Quality。[Constant Quality vs Average Bit Rate](https://handbrake.fr/docs/en/latest/technical/video-cq-vs-abr.html) 维护者在 GitHub 讨论中明确：目标文件大小功能多年前已移除，因为准确性不足、投诉不断（[Issue #4640](https://github.com/HandBrake/HandBrake/issues/4640)）。官方预设里的 Social 系列是例外：针对特定时长与 25 MB 上限（如 Discord），不是任意目标体积。[官方预设说明](https://handbrake.fr/docs/en/latest/technical/official-presets.html)
- **本地还是上传**：本地。
- **主要平台**：Windows、macOS、Linux。免费开源。
- **价格**：免费。本轮未在官网看到售价。
- **适用人群**：愿意理解预设、编码器和画质档位的用户；能力强，但入门成本高。

### 4.3 用户还会拿来解决同一问题的替代方案

这些不是同一细赛道上的直接竞品，却是用户今天的真实去路。

**格式工厂。** [官网](https://www.pcgeshi.com/) 显示 Windows 桌面版 5.22.4，更新于 2026-11-11，官方称免费、无需注册，并列出「多媒体文件压缩减肥」、批量转换等。定位是万能格式转换，压缩只是其中一项。本轮**未能从桌面端官网页直接核实**「可输入目标体积」的控件；仅在第三方教程中见到输出配置里的大小限制，故桌面端是否一等支持「指定目标大小」记为未核实。官方手机版内容有压缩与参数说明，与 PC 版不能自动等同。[手机版参数说明](https://m.pcgeshi.com/faq/shipin-shezhi.html) 是知识介绍，不足以为 PC 版功能背书。对我们的意义：它是很多国内用户的默认「先丢进格式工厂」；我们比的不是格式覆盖，而是目标体积是否好用、快不快、清不清晰、是否把文件上传（它是本地软件）。

**剪映 / 同类导出。** 用户常在剪辑软件里靠降低分辨率、帧率、码率或改用 H.265 把导出体积做小。这是「用编辑器顺便压缩」，不是输入目标 MB。本轮访问剪映专业版官网超时，**未能从官方帮助核实**它是否提供「指定目标文件大小」。第三方教程多写自定义码率，不能当作官方功能清单。对我们的意义：若用户已经在剪映里出片，可能会在导出时顺便压小；我们服务的是「手里已经有一条成品视频，只想按大小再压一次」的人，不应把第一期做成剪辑器。

**ffmpeg 命令行。** 本地、可控、能做 libx265 双遍并按码率逼近目标体积，是我们技术路径的底层能力，也是进阶用户的直接替代。官方文档站点为 [ffmpeg.org](https://ffmpeg.org/)；FFmpeg Wiki 的 H.265 页面本轮抓取被反机器人校验拦截，具体官方示例命令不在此转抄。对我们的意义：命令行对目标用户门槛过高。产品价值是把「算码率、跑两遍、加 `hvc1` / faststart、处理失败与临时文件」收成一次点击，并把速度/画质的选择做成可靠默认，而不是把命令行参数暴露出来。

**在线压缩网站。** 以 [FreeConvert Video Compressor](https://www.freeconvert.com/video-compressor) 为例：官方提供 “Target a file size”，也可按原大小的百分比压缩（官方甚至把按原大小百分比作为默认思路之一）。流程是选择文件后在网站上执行压缩并下载，属于把文件交给对方服务器处理的在线工具，不是本地应用。[官方定价与 FAQ](https://www.freeconvert.com/pricing) 写明免费用户每天 20 个 conversion minutes，单文件免费使用限制为 5 个 conversion minutes；付费档本轮页面可见 $12.99、$24.99 等标价，但各档完整权益、免费档最大上传体积等未能从该页完整核对，不补写未核实的数字。对我们的意义：在线工具往往「有目标大小、即开即用」，但要上传、受时长/配额限制、隐私与大文件都不合适。本地、无上传、无每日配额，是对这类工具的直接替代，而不是和它们比谁的页面功能更多。

## 5. 三期规划

切分理由：先把「一支视频：又快、又清晰、体积可控」做成立，再扩展到「更多文件更省事」，最后减少「压完才知道好坏」的意外。不按「功能清单凑版本」来切。批量、预设管理不回到第一期——即使第一期要重新评估硬件加速，也只为速度和画质服务，不因此把范围做大。

### 5.1 第一期 = MVP

**目标**

在功能保持极简的前提下，让单文件压缩同时满足：

1. **快**：等待时间可感知地短，过程可取消，进度诚实。
2. **画质高**：在用户给出的目标体积内，尽量保住观感；不放大、不裁切、不加黑边。
3. **体积可控**：输出围绕用户指定的目标大小，误差策略明确（具体容差待确认）。

第一期成功，看的是这三点，不是功能是不是够多。

**范围**

- 单窗口、单文件。拖入或选择视频，展示文件名、原大小、时长、分辨率。
- 目标大小默认原片 50%（四舍五入到整数 MB），数字输入与滑条双向同步；滑条与越界规则对齐需求文档。
- 开始 / 取消、压缩中进度、完成结果（路径、前后大小、打开文件、打开所在文件夹）、失败与拦截提示。
- 本地 ffmpeg；输出 1080p 上限的 HEVC `.mp4`，`hvc1` + `faststart`。
- 编码路径：在「libx265 软编双遍」与「硬件加速」之间按第 5.1.1 节验证后选定，不在第一期做编码器设置页。
- 输出位置、命名、分辨率与画面、音频、取消清理等，沿用原型 10 条默认假设（仍待确认）。
- 开始前拦截：非视频或不支持格式、目标 ≥ 原大小、磁盘空间不足、输出目录无写权限等，行为见需求文档。
- 界面：第一版浅色、接近 macOS 桌面应用；产品名展示为「快鸭鸭」，logo 用一只小黄鸭。深色模式待确认。
- 关于与反馈：第一期要有可找到的关于/反馈入口。写清维护者是「黑曼巴的紫金王朝」。反馈为邮箱 zhanglikunmamba@gmail.com + 微信扫码。二维码已定为 `assets/feedback-wechat-qr.png`，见第 5.1.3 节。不做成账号体系。
- 开通机制：不做登录和账号。用户输入服务端分发的 Key 即可使用；Key 可设有效期，到期自动失效。Key 只发给内部人，先小范围试用，不对外销售。使用 Key 时断网不能使用，网络用于校验 Key 的合法性。Key 过期只是不能开始压缩，仍可打开应用、查看或打开已有文件。未持有有效 Key，或无法完成校验时，不能开始压缩。校验失败须分开提示「网络不通」和「Key 无效或过期」。设备绑定为一对一：一台电脑只匹配一个 Key，一个 Key 同时只绑定一台电脑；换机和重装须管理员解绑后重绑原 Key；本机再输入另一枚 Key 则拒绝；第一次成功校验即绑定（细则见第 5.1.2 节，由昆哥小弟代为拍板，昆哥可随时改）。无感校验已拍板（可由昆哥改）：第一次仍要输入 Key；绑定成功后打开直接进主界面，后台静默校验，不弹开通页、不打断操作；点「开始压缩」时若这次已校验通过则直接开始、不再弹出「校验中」，若后台校验未完成则只在开始按钮上短暂等待、不进开通页、不大弹窗；只有失败才有感。必须联网校验，上次校验通过不能当离线通行证。

**不做项**

- 批量队列、多文件并行
- 预设方案的保存与管理（含「10 MB / 25 MB」快捷档，放到第二期）
- 自定义分辨率、帧率、编码器组合、码率模式的专业面板
- 自定义输出路径与文件名
- 登录、注册、账号体系、云同步；视频文件仍不上传（与服务端的来往仅用于 Key 校验，不把视频传上服务器）
- 图片、纯音频、GIF、文件夹监视、菜单栏常驻
- 压缩前后画面对比（第三期）

硬件加速不再默认写成「第一期明确不做」，改为「必须先验证再决定是否进入第一期默认路径」，见下节。

**关键体验**

- 开通后就能用，绑定后无感校验：第一次仍要输入 Key，这一步没法无感，也不要做成登录注册流程。绑定成功后，以后打开应用直接进主界面，对已绑定 Key 在后台静默校验，不弹开通页、不打断操作；打开即可拖入、确认默认一半或改一个数字。点「开始压缩」时，若这次打开后已经静默校验通过，直接开始，不再弹出「校验中」；若后台校验还没完成，只在开始按钮上短暂等待，不进开通页、不大弹窗。只有失败才有感：网络不通、Key 无效或过期，按已约定分开提示；过期只拦压缩，仍可打开应用和已有文件，并可重新输入 Key。必须联网校验合法性，不能把上次校验通过当作离线通行证。
- 速度被看见：进度不能长时间停在无法理解的状态；若走双遍，须区分「第一遍分析 / 第二遍编码」；若走硬件加速单段编码，不要假装还有两遍，进度文案要与真实路径一致。剩余时间只做粗略估算，不准时显示「计算剩余时间…」。
- 画质预期被守住：低于或等于 1080p 不放大；非 16:9 / 竖屏按比例缩放、长边不超过 1080，不裁切、不加黑边。
- 安全感：底部保留「本机处理，文件不会上传」；取消或关闭前确认，并删除临时文件、不改原片；完成不自动打开文件。
- 失败可恢复：说明原因，原片仍在，可改目标后重试或换文件。
- 关于和反馈找得到：用户能在应用里找到关于/反馈入口，看到维护者「黑曼巴的紫金王朝」，并用邮箱 zhanglikunmamba@gmail.com 或微信扫码反馈。不做成账号或个人中心。

**成功标准（围绕速度与画质，不是功能覆盖率）**

本轮没有可引用的实测耗时或画质分数，不编造「X 分钟压完」或「VMAF 达到多少」。第一期用下面这些可检验的标准：

1. **速度**
   - 在选定的默认编码路径下，对一组事先约定的样片（建议覆盖：手机 1080p 短片、1080p 会议/课件长片、4K 短素材）记录耗时，并与「libx265 较慢预设双遍」对照。默认路径必须明显快于这条对照基线，或在验证后被昆哥明确接受其耗时。
   - 压缩过程可随时取消，取消后迅速回到可再开始的状态，不留下半成品。
   - 进度与当前真实阶段一致，不出现长时间无反馈。
   - 不把「功能做全」当作速度已经达标。
2. **画质**
   - 在同一组样片、同一目标大小下，默认路径的观感应达到昆哥可接受的水平（建议用并排试看：人脸、文字/字幕、运动画面、暗部）。本阶段以人工审片为主，不先绑定某一个未选定的客观指标。

#### 5.1.1 编码路径交替：libx265 软编双遍 vs 硬件加速

这是第一期最重要的技术产品决策，必须写清楚，不能在方案里悄悄改掉既有定案。

既有定案是：Electron + 本地 ffmpeg，**libx265 双遍**，输出 1080p HEVC `hvc1` + `faststart`。原共识把硬件加速（VideoToolbox / NVENC 等）明确放到第一版之后。产品核心改为「要快，也要画质高」之后，第一期需要重新评估硬件加速，尤其是若首先做 macOS，应评估 VideoToolbox。

两条路径的利弊（定性，本轮不做未实测的倍数或分数对比）：

| | libx265 软编双遍（既有定案） | 硬件加速（macOS 上优先评估 VideoToolbox） |
| --- | --- | --- |
| 速度 | 通常更慢。双遍意味着先分析再编码，软编 HEVC 在长片、4K、高帧率上等待会很明显，直接冲击「要快」 | 通常明显更快，更贴近「要快」。这正是原共识需要被重新评估的原因 |
| 画质 | 在相近码率下，软编 x265 双遍一般更利于把码率用在复杂画面上，较符合「尽量保画质」 | 硬件编码器以速度见长，同等体积下画质是否可接受必须实测，不能默认等同于 libx265 |
| 目标体积 | 双遍平均码率是逼近目标大小的传统做法，仍须计入音频、封装开销，并验证是否会略超目标 | 速率控制往往更粗。CompressO 曾公开修复「macOS 硬编结果比原片大」和「Target Size 超出所选大小」，说明这条路径有体积失控风险 |
| 进度形态 | 与当前原型的「第一遍分析 / 第二遍编码」天然一致 | 可能不是经典双遍。若采用，进度文案要改成与真实过程一致，而不是套用两遍 UI 假装在做软编 |
| 产品复杂度 | 与既有定案一致，少一个决策 | 要处理设备差异、编码器是否可用、失败回退；第一期仍不应做成编码器设置面板 |

**建议方向（待昆哥确认，不是已经改写的定案）：**

1. **先验证，再锁定第一期默认路径。** 用同一组样片、同一个目标大小，对比 libx265 双遍与 VideoToolbox（若后续做 Windows，再单列 NVENC 等，不在未决定平台前写死）。记录三项：是否稳定落在约定的体积策略内、画质是否可接受、耗时差异。没有这组结果之前，不把既有 libx265 双遍定案直接换成硬件加速。
2. **若硬件加速能稳定满足体积策略、画质也被接受：第一期默认走硬件加速**，以兑现「快」。libx265 双遍保留为回退（硬编不可用或失败时自动改走软编），界面仍是一条「开始压缩」，第一期不增加「模式管理」。输出容器与标签仍遵守 HEVC `.mp4`、`hvc1` + `faststart`。
3. **若硬件加速经常超出目标，或画质明显不可接受：第一期仍以 libx265 双遍为默认**，以兑现「准」和「画质」。同时用更积极的 x265 速度预设、更好的进度与预期管理来缓解「慢」，而不是靠堆功能掩盖等待。硬件加速等验证过关后再作为默认或进入第二期。
4. **不建议第一期同时做一个给用户选的「更快 / 更好画质」开关**，除非验证表明两条路径都必须保留、且默认路径无法兼顾。功能简单优先；这条选择可以放到第二期。
5. **无论默认哪条路径，体积策略都要先拍板。** 若业务上「不得超过目标」（邮件、提交），硬编如果做不到「稳定不超」，就不能当默认，哪怕它更快。必要时可在内部以略低于用户目标的视频码率来预留音频和封装，这是实现策略，不是把目标改掉。

这一节的结论依赖实测，本方案不提前宣布「第一期已改为硬件加速」或「继续禁止硬件加速」。

### 5.3 第三期：更好判断画质、更少意外

**目标**

减少「等了很久才发现太糊、太大或不能播」。让用户在保存前更有把握，并在第一、二期的固定输出约定之外，提供少量真正有需要的规格，而不是开放全部参数。

- 无约束的编码器/滤镜实验室
- 在线处理

**关键体验**

- 用户不必把文件拖到播放器里来回对比，就能判断这次能不能用。

- 需要兼容旧设备时，有明确的一条出路，而不是让用户自己去找另一款软件碰运气。

**成功标准**

- 对比功能能支持「接受结果 / 改目标重来」的判断，而不是仅作展示。
- 新增输出规格有对应场景，且体积策略、速度预期仍然成立。
