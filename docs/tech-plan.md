## 1. 结论摘要

做一款名为「快鸭鸭」的 macOS 桌面小应用：Electron + TypeScript 壳，本机打包 ffmpeg / ffprobe，视频全程不上传。第一期只做单文件主路径，功能与已拍板原型对齐（含 Key 开通、无感校验、关于/反馈）。

架构上把「会碰到文件、进程和网络的事」全部放在主进程：探测媒体信息、编码、取消与临时文件清理、磁盘和权限检查、Key 校验、设备标识、打开文件/访达。渲染进程只做界面和状态展示，通过预加载脚本调用白名单 IPC，不允许直接跑 Node 或拉起 ffmpeg。

编码上同时实现两条路径，但**第一期默认走哪条先不定死**：

1. 既有定案：`libx265` 软编双遍，进度与当前原型的「第一遍分析 / 第二遍编码」一致。
2. 候选：macOS `hevc_videotoolbox` 硬编（通常是单段），进度文案必须改成与真实过程一致，不能套两遍 UI 假装在软编。

启动时探测本机是否可用 VideoToolbox，并把探测结果记下来，供验证和日后回退使用。默认路径等在昆哥 Mac 上用约定样片对比速度、画质、体积后再由昆哥拍板（验证方法见第 7 节）。无论默认哪条，输出约定不变：长边不超过 1080 的 HEVC `.mp4`，`hvc1` + `faststart`；硬编不可用或失败时自动回退软编，界面仍是一颗「开始压缩」，不做编码器设置页。

Key 校验做成薄门禁，不是账号体系。Key 与设备 ID 放进系统钥匙串，不进明文配置。必须每次联网校验，内存里的「本次已通过」只在这次进程有效，磁盘上的上次成功不能当离线通行证。交互与现行原型一致：首次输入；绑定后打开直进主界面并后台静默校验；点开始时已通过则直接压，未完成则只在开始按钮上短暂等待；只有失败才提示，且「网络不通」与「Key 无效或过期」分开；过期只拦压缩。

第一期平台按已确认范围：只做 macOS，Windows 后补。建议优先打 Apple Silicon 包；是否同时出 Intel / Universal、最低系统版本、是否公证，见第 12 节待确认项。

## 2. 已拍板约束（本方案不改）

- 单文件；读到原片后默认目标为原大小一半（四舍五入到整数 MB），数字与滑条可调。
- 不做账号；Key 开通；一对一设备绑定；第一次成功校验即绑定。
- 无感校验五条（首次须输入；绑定后打开直进主界面并后台静默校验；本次已通过则点开始直接压，未完成则只在开始按钮上短暂等待；只有失败才提示；必须联网校验，上次通过不能当离线通行证）。
- 失败分开提「网络不通」与「Key 无效或过期」；过期只拦压缩，仍可打开应用和已有文件。
- 关于/反馈：维护者「黑曼巴的紫金王朝」，邮箱 `zhanglikunmamba@gmail.com`，微信二维码用产品方案同一张图。

## 4. Electron 架构

### 4.1 进程职责

```
主进程（Node，可信）
  单实例锁、BrowserWindow、电源/关闭事件
  拉起并监管 ffmpeg / ffprobe 子进程
  钥匙串、设备 ID、Key API
  文件对话框、磁盘与权限检查、打开文件/访达
        │ IPC（preload 白名单）
        ▼
渲染进程（无 Node）
  按原型状态机画界面、收进度、点按钮
```

硬性约定：

- `contextIsolation: true`，`nodeIntegration: false`，渲染进程 `sandbox: true`。
- 只开一个主窗口。压缩中点关闭交通灯，走与「取消」相同的确认；确认后先停任务、清临时文件再退出。
- 保持单实例：第二次打开只聚焦已有窗口。
- ffmpeg 工作目录和日志里不得出现完整 Key。

建议脚手架：`electron-vite` + `electron-builder` + TypeScript strict。打包出内部试用用的 `.dmg` / `.zip` 即可，不走应用商店，除非昆哥另定。

### 4.2 预加载 API（渲染进程只许走这里）

```ts
window.kuaiyaya = {
  selectVideo(): Promise<string | null>
  probe(filePath: string): Promise<ProbeInfo>
  checkStartGuards(input: StartInput): Promise<GuardResult>
  startCompress(input: StartInput): Promise<void>
  cancelCompress(): Promise<void>
  onCompressProgress(cb: (e: ProgressEvent) => void): () => void
  onCompressDone(cb: (e: DoneEvent) => void): () => void
  onCompressFail(cb: (e: FailEvent) => void): () => void
  openFile(filePath: string): Promise<void>
  revealInFinder(filePath: string): Promise<void>
```

`StartInput` 只包含原片路径和目标大小（整数 MB）。编码器选择不暴露给渲染进程。

## 5. 编码子系统

### 5.1 读原片

用打包的 `ffprobe` 读：容器、视频编码、宽高、旋转标签、时长、音频轨。文件大小用文件系统。任一必备字段读不到，或没有视频流，按「不支持此文件，请选择视频」拒绝，不进入「已选文件」。

拖入多个文件时只接受第一个有效视频；全无效则按非视频提示。压缩过程中再拖入的文件直接忽略。

**输入白名单（建议，待昆哥确认）：** 容器至少 `mp4` / `mov` / `m4v` / `mkv` / `webm` / `avi`。最终仍以 `ffprobe` 能否读到视频流为准；需要时再把失败文案写得更具体，第一期可以先用原型这句统一提示。

### 5.2 画面与音频（沿用 10 条假设）

- 长边大于 1080：按比例缩放，长边 1080，不裁切、不加黑边；宽高都做成偶数，避免 yuv420 编码失败。
- 长边已经 ≤ 1080：不放大，按原分辨率编码。
- 尊重 `rotate` / `displaymatrix`，避免竖屏被当成横屏。
- 音频统一转 AAC 128 kbps，不拷贝原轨。无音轨则只出视频，不因此失败。
- 封装：`.mp4`，`-tag:v hvc1`，`-movflags +faststart`。

### 5.3 目标体积怎么落到码率

```
可用比特 = 目标字节 × 8 × 安全系数
视频码率 = max(最低视频码率, 可用比特 / 时长 − 音频码率 − 封装预留)
```

安全系数建议先按 0.93～0.95 做，给音频、moov 和硬编波动留余量；这是实现策略，界面上的目标数字不改。最低视频码率过低时仍开压，但可能明显发糊（画质风险提示在第三期，第一期不做）。

**体积策略仍待昆哥拍板**（不得超过 / 允许小幅误差 / 偶发略超也可算成功）。策略不定，硬编能不能当默认也无法判断。本方案按「尽量一次压到目标附近，并预留余量」实现；若拍板为「不得超过」，完成时若仍超出目标，该次不能标为成功（软编应极少发生；硬编可能要一次有限重试，次数要写死，避免把「快」吃掉）。未拍板前，验证记录里同时写「是否超过目标」和「偏差百分比」，供拍板用。

### 5.4 两条编码路径（都要实现，默认先空着）

**路径 A：`libx265` 双遍（既有定案）**

1. 第一遍：`-pass 1`，无音频，输出到 null，只分析。进度文案：「第一遍 分析画面」。
2. 第二遍：`-pass 2`，写入临时 mp4，带音频、`hvc1`、`faststart`。进度文案：「第二遍 编码输出」。
3. 预设建议先用 `medium` 或略快的 `fast` / `veryfast` 做对照，不在界面上让用户选。最终预设跟默认路径一起在样片验证后确定。
4. pass log 放在临时目录，结束或取消后删除。

**路径 B：`hevc_videotoolbox`（候选默认）**

1. 通常只有一段编码，进度是单条「正在编码」，不要画两条假的分析/编码。
2. 用略保守的码率（或等效质量参数）去逼近目标。VideoToolbox 的码率控制比 x265 双遍粗，这是已知风险（CompressO 也公开修过「硬编比原片还大 / 超出 Target Size」）。
3. 若拍板「不得超过」且第一次略超，允许自动再压一次（略降码率），最多 1 次重试，界面仍算同一次任务，进度重置并给简短说明，不要做成用户可感知的「模式切换」。

默认路径用主进程配置项（或构建期开关）指定，**先保持显式未选定**。未选定前，开发与验证可以手动指定路径，正式包不带「更快 / 更好画质」开关。

硬编探测失败、进程非 0 退出且判断为编码器不可用时：自动改走路径 A，并在失败无可回退时才进失败页。回退对用户仍是一次「开始压缩」。

### 5.5 进度、取消、临时文件

- 用 ffmpeg 的 `-progress` 管道解析出当前时长，除以总时长得到该段百分比。剩余时间只做粗略估算，数据不够时显示「计算剩余时间…」。
- 「取消」先弹与原型相同的确认。确定后杀掉 ffmpeg 进程组，删除临时文件（部分 mp4、pass log），原片不动，回到「已选文件」并提示已取消。取消不可从中断点续压。
- 输出先写到同目录临时名（例如 `原名_1080p.mp4.partial`），成功并做完 faststart 后再改名为最终名。最终名冲突时自动加 ` (2)`、` (3)`，不覆盖、不额外弹窗。
- 编码非 0、中途盘满、原片被占用或消失：进失败页，说明简要原因，清理临时文件，原片不改，可重试。打开已完成结果时若文件已被删走，提示「文件已不在原位置」。

开始前拦截（与需求文档一致，用对话框，不创建临时文件）：

- 目标 ≥ 原大小：「原片已经不大于目标大小，无需压缩。请调低目标后再开始。」
- 磁盘可用空间需大于「目标大小 + max(200MB, 目标的 20%)」。
- 输出目录无写权限。

## 6. ffmpeg 集成与打包

- **不依赖**用户机器上的系统 ffmpeg。正式包用 `extraResources` 带上与当前架构匹配的 `ffmpeg`、`ffprobe`，运行时按 `process.arch` 选目录。
- 带上的二进制必须同时编入：`libx265`、`videotoolbox` / `hevc_videotoolbox`、AAC、常用 demuxer。这通常意味着 **GPL** 构建（x265）。第一期是内部试用，也要在方案里标明这一点；若以后只保留硬编、去掉 x265，才可能改用 LGPL 构建。不把未审查的「网上随便下一个 ffmpeg」写进发布清单。
- 二进制放到 asar 包外（`extraResources` 或 `asarUnpack`），并赋予可执行权限。主进程只通过绝对路径调用，不改 `PATH`。
- 签名与公证（待确认）：Electron 自身要签；ffmpeg 若未签，hardened runtime 下可能起不来，需要一并签名或补对应 entitlements。CompressO 因费用公开表示未做公证；本方案不假设已有苹果开发者账号。内部试用若先不公证，须接受「未识别的开发者」这一打开方式，并在发放说明里写清楚。
- 第一期建议先打 `darwin-arm64`。若昆哥或试用机有 Intel Mac，再补 `darwin-x64` 或 Universal。Windows 的 ffmpeg / NVENC 不进入第一期包。

开发阶段可在本机用一份合格的 ffmpeg 做联调，但 CI / 打包脚本要把「用的是哪一版、哪些 encoder」写进关于页或日志，避免验证和生产用的不是同一份二进制。

## 7. 硬件加速探测，以及如何在昆哥 Mac 上验证

### 7.1 探测（应用每次启动做一次，不锁定默认）

主进程在窗口出来后后台执行，不挡启动：

1. `ffmpeg -hide_banner -encoders` 是否包含 `hevc_videotoolbox` 与 `libx265`。
2. 若声明支持 VideoToolbox，再用极短的空任务或 1 秒样片试编，确认进程能以 0 退出（仅声明支持但初始化失败的机器，视为不可用）。
3. 结果写入 `EncoderCaps`：`{ x265: boolean, videotoolbox: boolean, ffmpegVersion, probedAt }`，供日志和关于页（可选）查看。

探测失败只表示「本机这条路径不可用」，**不能在未拍板时把默认改成硬编或禁掉硬编**。即使探测成功，正式默认仍等第 7.2 节的样片结论和昆哥拍板。

### 7.2 样片验证方法（写清怎么做，本轮先不动手）

地点：昆哥 Mac。使用与正式包同一套 ffmpeg。不要用系统自带的其它发行版代替。

**建议样片（与产品方案成功标准对齐，具体文件由昆哥指定或提供）：**

| 编号 | 类型 | 建议特征 |
| --- | --- | --- |
| S1 | 手机 1080p 短片 | 数十秒到两三分钟，有人脸、运动 |
| S2 | 1080p 会议 / 课件长片 | 十数分钟以上，有文字、字幕、相对静止 |
| S3 | 4K 短素材 | 需要缩小到 1080p 上限，看缩放和细节 |

同一文件、同一目标大小（默认「原大小一半」，并再抽一档更小的目标做对照），分别跑路径 A 和路径 B。记录：

- 耗时（从点开始到文件落盘）
- 输出体积、是否超过目标、偏差百分比
- 封装是否为 HEVC + `hvc1` + `faststart`（`ffprobe` 检查）
- 人工审片：人脸、文字/字幕、运动、暗部（并排播放，不先绑定 VMAF 等分数线，除非昆哥要求）
- 硬编是否出现明显块面、发糊、或体积失控；软编等待是否不可接受

验证用脚本只接受明确的 `--encoder x265|videotoolbox` 参数，不读取「默认路径」配置，避免误把某次实验结果写进产品默认。本技术方案通过后、写代码阶段再补脚本；**现在不在昆哥机器上跑、不定死默认**。

**拍板规则（沿用产品方案 5.1.1，不另发明标准）：**

- 硬编能稳定落在约定体积策略内、画质昆哥可接受：第一期默认硬编，软编作回退。
- 硬编经常超目标，或画质明显不可接受：第一期默认仍为 `libx265` 双遍，用更积极的 x265 预设和更老实的进度文案缓解「慢」；硬编过关后再考虑改默认或放到第二期。
- 第一期不给用户「更快 / 更好画质」开关，除非验证表明两条都必须保留且一条默认无法兼顾。

## 8. Key 校验客户端与无感校验

### 8.1 设备指纹（已与服务端第 6 节对齐）

不要单独用 `IOPlatformUUID`：重装系统后它通常还在，会绕过「须管理员解绑再绑」。也不要只用应用自己生成、只存在本地的 UUID：把钥匙串拷到另一台电脑就能占用绑定；加上硬件分量才能挡住这个。只删掉 App 再装、系统安装 ID 还在时，指纹应尽量不变，不必为此找管理员。

第一期采用 [key-service-plan.md](/workspace/plans/video-compressor-tech/key-service-plan.md) 第 6 节公式（客户端计算，服务端只收哈希做全等匹配，不收原始硬件信息）：

```
deviceId = SHA-256("kuaiyaya.v1" + "|" + hw_uuid + "|" + os_install_id)
```

得到 64 位小写 hex。其中：

- 盐值 / 标识：固定字符串 `kuaiyaya.v1`（不要写成 `kuayaya` 或 `kuaiyaya-fp-v1`）
- `hw_uuid`：`IOPlatformUUID`
- `os_install_id`：系统卷 Volume UUID（重装 / 格式化系统盘后通常会变）

第一期只定义 v1。以后改算法必须升版本并做迁移，不能让已绑定设备在升级后全部变成新设备。请求里不另传版本字段。

结果：应用更新、正常重启后指纹不变；重装系统、换硬盘、系统迁移导致安装标识变化时视为新设备。电脑名称只作管理展示（`deviceLabel`），不参与指纹。不要用 MAC 地址或主机名当绑定依据。算好的 `deviceId` 可以放进钥匙串以免每次启动重复计算，但不能把自行生成的随机 UUID 当作绑定 ID。

### 8.2 本地存储

钥匙串（service 如 `cn.kuaiyaya.desktop`）保存：规范化后的 Key，以及算好的 `deviceId`。不进明文 JSON，不用原型那种 `localStorage`。不使用、不保存 `bind_token`。

- 渲染进程看不到原始 Key（关于页只提示「已开通」即可）。
- 「本次打开后是否已静默校验通过」只放在主进程内存。进程退出即失效。磁盘上不得写 `lastVerifiedAt` 之类用来跳过联网的字段。
- 每次启动先按第 8.1 节计算当前 `deviceId`，再携带钥匙串里的 Key 做静默校验。若指纹已变，按校验失败 / `not_bound` 或 `key_bound_to_other_device` 处理，不要用旧指纹继续请求。

### 8.3 与服务端的契约（与 key-service-plan.md 对齐）

HTTPS，建议超时 8 秒，超时归入「网络不通」。视频文件绝不出现在这些请求里。Base URL 待后端提供，客户端做成可配置，正式包写入约定地址。

业务码与 [data-model.md](/workspace/plans/video-compressor-tech/data-model.md) 第 6 节、服务端方案第 5.4 节一致：`ok`、`invalid`、`expired`、`device_bound_to_other_key`、`key_bound_to_other_device`、`not_bound`。`invalid` 与 `expired` 对用户可共用「Key 无效或过期」，但接口必须分开；`not_bound` 不得并进这两码。分类不能合并。

**开通（第一次成功校验即绑定；validate 不会创建绑定）**

`POST /v1/license/activate`

```json
{
  "key": "KYDY-XXXX-XXXX-XXXX",
  "deviceId": "<64 位小写 hex，见第 8.1 节>",
  "appVersion": "1.0.0",
  "platform": "darwin",
  "arch": "arm64",
  "deviceLabel": "可选，电脑名称，仅管理展示"
}
```

成功 `data` 只有：

```json
{ "expiresAt": "2027-01-01T15:59:59.000Z", "serverTime": "2026-11-12T03:41:00.000Z" }
```

无期限时 `expiresAt` 为 `null`。成功后把 Key（及算好的 `deviceId`）写入钥匙串，进入主界面。

| error.code | 用户侧分类 | 客户端建议表现 |
| --- | --- | --- |
| `invalid` / `expired` | Key 无效或过期 | 「Key 无效或已过期…」；已绑定过期走横幅，仍可打开已有文件 |
| `key_bound_to_other_device` | Key 问题（单独文案） | 「该 Key 已绑定其他电脑。如需换机使用，请联系管理员先解绑。」 |
| `device_bound_to_other_key` | Key 问题 | 「本机已匹配其他 Key。如需更换，请联系管理员先解绑当前绑定。」 |
| `invalid_request` | 既不是 Key 无效，也不是网络不通 | 可提示重试 |
| 连不上 / 超时 / TLS 失败 / 5xx / 429 | 网络不通 | 「网络不通，暂时连不上服务端。请检查网络后再试。」 |

客户端在本地已有绑定 Key 时，若用户再输入另一枚，可先在本地用「已匹配其他 Key」拒绝（与原型 `key-bound` 一致）；服务端仍必须再判一次，不能只靠客户端。解绑是管理员在服务端做的，客户端第一期不提供解绑入口。

**静默校验 / 开始前校验（不绑定，不解绑后也不自动抢回）**

`POST /v1/license/validate`

```json
{
  "key": "KYDY-XXXX-XXXX-XXXX",
  "deviceId": "<与激活时相同>",
  "appVersion": "1.0.0"
}
```

必须带 Key 和 `deviceId`。Key 从钥匙串读取，供静默请求使用。不接受不带 Key，也不把校验当成绑定。不使用 `bind_token`。

成功 `data` 同激活，只有 `expiresAt`、`serverTime`。

| 结果 | 用户侧分类 | 客户端表现 |
| --- | --- | --- |
| `ok`（仍有效且就是这台设备） | 通过 | 本次内存 `verified = true` |
| `invalid` / `expired` | Key 无效或过期 | 拦压缩，横幅或对话框按原型；不说成网络不通 |
| `not_bound`（已解绑或两边都无绑定） | Key 问题，不说成网络不通 | 「当前绑定已解除或设备身份已变化，不能开始压缩。请联系管理员，或重新输入 Key。」仍可打开已有文件，不自动改绑 |
| `key_bound_to_other_device` | Key 问题 | 指纹已变但原 Key 仍被旧指纹占用时可能走到这里；拦压缩，引导联系管理员解绑 |
| 连不上等 | 网络不通 | 按原型「网络不通」提示 |

两次接口都必须能让客户端区分「网络问题」和「Key 问题」，不能只返回一个笼统的 false。用户可见文案由客户端按 code 映射，不直接展示服务端 `message`。

### 8.4 无感校验状态机（与现行原型对齐）

```
启动
  ├─ 钥匙串没有绑定 Key → 只显示开通页（screen-key），不进主界面
  └─ 已有绑定 Key → 直接进主界面（空闲；若有「最近一次输出」可展示打开入口）
                      同时后台 validate
                        ├─ 成功：内存 marked verified
                        └─ 失败：主界面保留，顶栏横幅有感提示
                           （网络不通 / Key 无效或过期 / 绑定已解除或设备身份变化，后两类都不当成网络问题）
                           仍可查看、打开已有文件，不能开始压缩

点「开通」
  按钮进入校验中，输入框禁用
  按 8.3 分类展示行内错误或成功后进入主界面

点「开始压缩」
  ├─ 本次已 verified 且状态有效 → 直接开始，不弹「校验中」
  ├─ 后台校验还在进行 → 按钮进入短暂等待（文案用原型的「请稍候…」），不进开通页、不大弹窗
  │     成功则自动开始；失败则结束等待，按分类弹对话框
  └─ 已经失败或尚未开通 → 不开始，按原型弹对应对话框
       网络不通：「这不是 Key 无效或过期，也不是编码失败。」
       过期/无效：可「重新输入 Key」；过期不删本机文件
```

横幅与对话框文案直接采用现行原型，不另造一套。重新输入 Key 只在失败后需要换 Key、或管理员解绑后重新绑定时进入开通页。

关于页不依赖 Key 状态，未开通时也应能打开（原型标题栏在开通页也能点「关于」）。

### 9.3 可测的界面验收清单

下列均可对照原型手动走通，作为界面完成标准（编码可用 mock 进度，Key 可用 mock 服务端，但分类和时序必须真）：

**开通与无感校验**

- [ ] 过期只拦压缩，不删本机文件，不强制留在开通页。

**主路径**

- [ ] 拖放与「选择视频」均可；多文件只取第一个有效视频；非视频 toast「不支持此文件，请选择视频」，不进入 `screen-ready`。

## 10. 安全、隐私与日志

- 视频、截帧、码率日志都只落在本机。Key 校验请求只含 Key、设备 ID、应用版本和平台，不含文件路径和文件名。
- Key、设备 ID 进钥匙串；日志对 Key 做脱敏。
- 渲染进程不能读任意路径：只能处理用户选中或拖入、并经主进程校验过的路径。
- 正式包校验必须走 HTTPS。内部调试若用环境变量改 Base URL，不得在正式包里留后门跳过校验。
- 取消和失败必须删掉半成品，避免把未完成的 `.partial` 留在用户目录里误导。

## 11. 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 硬编打不中目标体积 | 行业里已有公开先例 | 码率预留余量；「不得超过」若拍板，最多 1 次自动再压；验证不过就不要把硬编当默认 |
| 硬编画质达不到软编 | 同等体积下不保证观感 | 样片并排审片后再拍板，不按未实测倍数宣传 |
| 软编太慢，伤「要快」 | 长片、4K 上双遍会很明显 | 用样片对照耗时；可用更快 x265 预设换部分画质，仍须昆哥接受 |
| ffmpeg 打包与签名 | hardened runtime 下未签名的子进程可能无法启动 | 与 Electron 一并签；公证与账号待确认 |
| GPL（libx265） | 带 x265 的 ffmpeg 通常是 GPL | 内部试用先标明；对外分发前要单独看法务，本方案不假设已对外授权 |
| 设备指纹选错 | 只用硬件 UUID 会在重装系统后仍能直接压；只用本地随机 ID 会在重装 App 后误找管理员，也能把钥匙串拷到另一台电脑占用绑定 | 采用已定 v1：`SHA-256("kuaiyaya.v1" + "|" + IOPlatformUUID + "|" + 系统卷 UUID)`，服务端只存哈希；指纹变了按 `not_bound` 处理 |
| 服务端未就绪 | 客户端门禁无法验收 | 先定契约；本地可用 mock 跑界面，但正式包必须连真服务端。上次成功绝不能当离线通行证，包括开发模式 |
| 与后端错误码对不齐 | 网络和 Key 问题被混成一类 | 本方案把分类写死，联调时作为验收项 |
| 竖屏 / 旋转 / 稀有容器 | 探测或缩放出错 | 样片里至少包含一支竖屏手机录像；白名单待确认 |

## 12. 待昆哥确认

下列两项产品方案里仍待确认，但会影响实现细节，建议尽快拍板：

1. **目标体积误差策略**（优先，和默认编码路径绑在一起）：成功是「不得超过目标」，还是「允许在目标上下某一明确幅度内」，还是「尽量接近、偶发略超也可标为成功」？本方案实现上会预留余量；若定为「不得超过」，完成时超标不能标成功。
2. **输入格式白名单**：是否同意第 5.1 节建议的常见容器列表？不支持时第一期是否沿用统一文案「请选择视频」？
3. **HEVC 兼容性说明**：完成页是否加一句「部分旧设备可能无法播放」，还是完全放到第三期？
4. **最低 macOS 版本与包架构**：建议 macOS 13 + 先出 Apple Silicon；是否要同时做 Intel？
5. **公证 / 开发者账号**：内部试用是否接受未公证的打开方式？
6. **画质验收**：是否指定固定样片包，或第一期就绑定某个客观指标？（本方案建议先人工审片。）
7. **「Key 已绑定其他设备」的文案**：是并入「Key 无效或过期」，还是单独一句请联系管理员解绑？
8. **仓库路径**：是否就用 `/Users/zhanglikun/workspace/app/kuaiyaya`？

以下已在任务里确认，本方案按此执行，不再当作开放问题：第一期只做 macOS；默认编码路径先验证再拍板，不在方案或代码里先写死。

## 14. 本方案的理解与假设

- 「会话式」的开通不是登录：没有注册、找回密码、个人中心、多账号。
- 一对一绑定的「一台电脑」以客户端按已定 v1 算法算出的 `deviceId` 为准（`SHA-256("kuaiyaya.v1" + "|" + IOPlatformUUID + "|" + 系统卷 UUID)` 小写 hex），不是单独的硬件序列号，也不是仅存在本地的随机 UUID。静默校验必须带 Key 和 `deviceId`，成功响应只有 `expiresAt`、`serverTime`，不使用 `bind_token`。错误分类不合并。
- 第一期不做 Windows，方案里不设计 NVENC。
- 不做文件夹监视、菜单栏常驻、批量、预设、自定义输出路径、编码器设置页。
- 产品方案第 7.3 节里「是否只做 macOS」在本任务中已确认只做 macOS；其余 7.3 项仍待确认。
- 后端 API 路径和字段名以第 8.3 节为客户端提案，后端可改名，但错误分类不能合并。
- 本轮不在昆哥 Mac 上跑样片、不安装依赖、不创建业务仓库、不改原型目录。
